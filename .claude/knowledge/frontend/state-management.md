# State management

Два разных вида состояния, две разных библиотеки — не смешивай их зоны ответственности.

## TanStack Query — серверное состояние

Всё, что приходит с бэкенда и туда же уходит: список приложений, документ приложения, сохранение (`PUT`), создание, удаление, экспорт. Хуки лежат в `packages/api/src/apps/queries.ts` и переиспользуются как есть — `shared/api` в `apps/web` только настраивает `QueryClient` и прокидывает его в `QueryClientProvider` в `app/`.

Не держи копию документа приложения в Zustand «для скорости» — источник истины один, TanStack Query кеш. Мутации (`useSaveApp` и т.п.) сами инвалидируют/обновляют кеш.

`QueryClient` в `shared/api/queryClient.ts` создан с `networkMode: "always"` для queries и mutations — без этого в некоторых окружениях (замечено в headless/встроенном браузере при разработке) `navigator.onLine`/внутренний online-detector TanStack Query залипает в `false`, и запросы уходят в `fetchStatus: "paused"` навсегда — ни `isLoading`, ни `isError` не становятся `true`, страница просто виснет в пустом состоянии без единой ошибки в консоли. `networkMode: "always"` убирает этот детектор из уравнения — запрос либо проходит, либо реально фейлится, без вечного псевдо-офлайна.

## Zustand — клиентское состояние редактора

То, чего на бэке нет и быть не должно: состояние доски и инспектора, которое существует только пока открыта вкладка.

**Основной стор — `entities/app-document/model/store.ts` (`useAppDocumentStore`)**, перенесён из рабочего прототипа (`webb/src/store/app-store.ts`) почти без изменений — Zustand + Immer middleware, держит:

- сам `document: AppDocument | null` (единственный источник правды для клиентского редактирования — на сервер уходит через `useSaveApp` из `packages/api`, с сервера приходит через `useApp`)
- выделение: `selectedScreenId`/`selectedNodeId`/`selectedNodeIds`/`selectionFrame`
- буфер обмена для copy/paste
- историю отмены/повтора: `past`/`future` — полные снимки документа (не патчи), лимит 50, склейка правок по `coalesceKey` в течение 900мс (drag/resize/ввод текста не спамят историю отдельной записью на каждый пиксель/символ)
- `aiBatch` — пока правки от ассистента идут пачкой (`beginAiTurn`/`endAiTurn`), промежуточные `pushPast` подавляются, весь пакет — одна запись истории
- `saveStatus`/`saveError`/`lastErrors` (последнее — предупреждения на русском, например «Слой закреплён», «Нельзя удалить корень экрана»)

Это осознанно **один большой стор**, не россыпь маленьких по виджетам — canvas/layers/inspector/ai-dock все правят один и тот же документ и должны видеть согласованную историю и выделение. Не дроби его на отдельные сторы по виджетам без веской причины.

Что НЕ портировано из прототипа: `persistAppHistory`/`loadAppHistory` (сохранение истории в `sessionStorage`) — в оригинале уже отключено с комментарием «restoring stale trees and fighting edits», код был мёртвый, порт не имел смысла.

Кроме этого стора — состояние, которое действительно локально одному виджету (позиция/зум доски, свёрнуты ли колонки чата/файлов, черновик текста в поле ввода до отправки) заводи рядом с этим виджетом, не тащи в общий стор.

## Где стык

Когда пользователь принимает предложение ассистента или сохраняет ручное изменение — Zustand-стор истории пишет снимок, а фактическое сохранение на бэк идёт через мутацию TanStack Query (с debounce 1200 мс, как описано в `product.md`). Эти две системы не подменяют друг друга: Zustand — что видно прямо сейчас на экране, TanStack Query — что подтверждено сервером.
