# Frontend — обзор

## Стек

- React 19 + React Compiler (автоматическая мемоизация, `babel-plugin-react-compiler` подключён в `@vitejs/plugin-react`) — не пиши руками `useMemo`/`useCallback`/`React.memo` без явной причины, компилятор берёт это на себя.
- TypeScript, строгий режим, без `any`.
- Vite — сборка и dev-сервер.
- React Router — роутинг (SPA, без SSR).
- Zustand — клиентское состояние редактора. TanStack Query — серверное состояние (данные с бэка). Разделение описано в [state-management.md](state-management.md).
- pnpm workspaces + Turborepo — монорепо.

## Структура

```
frontend/
├── apps/
│   ├── web/        # редактор + лендинг, всё, что сейчас реализуется
│   └── mobile/      # зарезервировано под будущее RN-приложение, кода пока нет
└── packages/
    └── api/          # типы + REST-клиент + TanStack Query хуки, без UI — общее для web и будущего mobile
```

`apps/mobile` пока пустой (только `README.md`). Когда до него дойдёт очередь — это будет Expo-приложение, использующее `packages/api` как есть и повторяющее функциональность веба, но с собственным UI-слоем (RN не рендерит DOM/CSS, весь UI-кит и вся доска/инспектор/чат пишутся заново под RN-примитивы). Не пытайся заранее абстрагировать UI ради переиспользования между платформами — переиспользуется только `packages/api` (модели данных и доступ к ним), это осознанное решение, см. обсуждение в истории проекта.

## Зачем `packages/api` — отдельный пакет, а не часть `apps/web/src/entities`

Чтобы форма `AppDocument` и способ ходить в бэк были одной точкой правды, а не дублировались, когда появится `apps/mobile`. Пакет исходниковый (без отдельного build-шага) — `apps/web` резолвит его напрямую через алиас `@bildo/api` в `tsconfig`/`vite.config.ts`, никакой компиляции на промежуточном шаге нет.

## Что уже перенесено из рабочего прототипа

Функциональность редактора портирована из Next.js-прототипа (`webb/`) на этот стек: доска с панорамированием/зумом, канвас с drag/resize/snap/мультивыделением, инспектор, док вставки с палитрой (Ctrl+K), чат ассистента с карточками предложений и коммитов, панели файлов и кода, кодоген `AppDocument` → Expo-проект, автосохранение, горячие клавиши, публичное превью.

Что **не** портировано осознанно:
- `AppLayersPanel` (панель слоёв, 558 строк) — в прототипе не импортирована ни одним живым файлом, мёртвый код; в ТЗ её тоже нет. Не тянем ради неё `@dnd-kit`.
- Шаблоны генерации приложения (`lib/app/templates/*`) и команда «пересобери» в чате — генерация `AppDocument` из промпта живёт на бэкенде (`POST /api/apps`), это не территория фронта.
- `zipStoreFiles` — zip собирает бэкенд на `GET /api/apps/[id]/export`, фронту он не нужен.
- Legacy сайт-билдера (`components/editor/*`, `lib/html-renderer/*`, `store/site-store.ts`, `components/onboarding/*`) — ретировано ещё в прототипе. Единственное, что оттуда пришлось забрать, — контрол `AlignPad`, он лежит в `shared/ui`.

## Единый кодстайл

- **Prettier** — форматирование (`.prettierrc.json`: 120 символов, двойные кавычки, точки с запятой, висячие запятые). Спорить о форматировании не нужно, `pnpm format` расставит всё сам.
- **ESLint 9, flat config** (`eslint.config.js` в корне `frontend/`) — один прогон на весь монорепо, а не по пакетам: конфиг общий, а типо-зависимым правилам нужен единый TS-контекст.
- **EditorConfig** (`.editorconfig` в корне репозитория) — базовые отступы и переводы строк, в том числе для `backend/`.

Что включено в линтер и почему:

- `typescript-eslint` в режиме `recommendedTypeChecked` + `stylisticTypeChecked`. `strictTypeChecked` намеренно **не** берём: он воюет с идиомами React (`no-confusing-void-expression` ругается на каждый `onClick={() => setOpen(false)}`) — сотни правок без выигрыша в надёжности.
- `eslint-plugin-react-hooks` в конфиге `flat["recommended-latest"]` — там не только правила хуков, но и проверки **React Compiler**: `purity`, `set-state-in-render`, `refs`, `immutability`. Именно они ловят классы ошибок, которые компилятор иначе молча оптимизирует неправильно.
- `eslint-plugin-boundaries` — **границы слоёв FSD** (см. [fsd.md](fsd.md)). Правило проверено на живых примерах: `shared → widgets` и `entities → features` падают, `widgets → shared` проходит. Для работы обязателен `eslint-import-resolver-typescript`: без него плагин не разворачивает алиас `@/` и `index.ts` в папке слайса — и молча считает все импорты «неизвестными», то есть тихо ничего не проверяет.
- `eslint-config-prettier` — последним, гасит правила, конфликтующие с форматтером.

Два правила намеренно ослаблены, не трогай без причины:
- `prefer-nullish-coalescing` с `ignorePrimitives: { string: true }` — `node.props?.text || "Текст"` по всему коду осознанно подставляет запасное значение и для пустой строки; `??` этого не сделает и поменяет поведение.
- `unbound-method` выключено — экшены Zustand и колбэки из пропсов передаются как значения повсюду, правило рассчитано на классы с `this`.

## Команды

Из `frontend/`:
- `pnpm install` — поставить зависимости для всего workspace
- `pnpm dev` — запустить `apps/web` в дев-режиме (Turborepo раскидает по пакетам)
- `pnpm build` — прод-сборка
- `pnpm lint` / `pnpm lint:fix` — линтер и автоисправление
- `pnpm format` / `pnpm format:check` — Prettier
- `pnpm typecheck` — `tsc --noEmit` по пакетам
- **`pnpm check`** — формат + линт + типы одной командой (то, что стоит гонять перед коммитом и в CI)
- **`pnpm fix`** — отформатировать и починить всё автоисправимое
