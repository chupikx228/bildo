# API-контракт фронт↔бек

Источник: раздел 5 ТЗ плюс сверка с рабочим прототипом (Next.js-версия продукта, которую делал предыдущий разработчик — там эти эндпоинты реально реализованы и работают на Drizzle/SQLite). Это отправная точка для FastAPI-реализации Егора, не финальная спецификация — он может её скорректировать, тогда правь и этот файл синхронно с `frontend/packages/api/src/apps/queries.ts`.

## Эндпоинты — формы запроса/ответа проверены по рабочему коду

| Метод | Путь | Тело запроса | Тело ответа |
|---|---|---|---|
| GET | `/api/apps` | — | `{ apps: AppSummary[] }` — `AppSummary = { id, name, slug?, updatedAt }`, сортировка по `updatedAt desc` |
| POST | `/api/apps` | `{ prompt: string, name?: string }`, `prompt.length >= 3` | `{ id: string }`, статус 201 |
| GET | `/api/apps/[id]` | — | `{ id, name, slug?, document: AppDocument, generationStatus, generationError? }` |
| PUT | `/api/apps/[id]` | `AppDocument` целиком | `{ ok: true, document: AppDocument }` |
| DELETE | `/api/apps/[id]` | — | `{ ok: true }` или 404 |
| GET | `/api/apps/[id]/export` | — | `application/zip`, не JSON |
| GET | `/api/tasks/[id]` | — | `{ id, status, result?, error? }` — статус фоновой задачи |

Все ответы об ошибках — JSON с полем `error`, человекочитаемый текст на русском.

## Асинхронная генерация приложения

`POST /api/apps` **форму ответа не меняет** — по-прежнему `{ id }` и 201. Но приложение создаётся сразу, с пустым плейсхолдер-документом (валидная тема, `screens: []`) и полем `generationStatus: "pending"`, а сама генерация уходит в очередь Arq. Клиент получает `id` немедленно и открывает редактор, не дожидаясь генерации.

`generationStatus` в ответе `GET /api/apps/[id]` — одно из трёх значений:

| Значение | Что означает |
|---|---|
| `pending` | документ ещё генерируется, в `document` лежит плейсхолдер без экранов |
| `ready` | генерация закончилась, в `document` готовое приложение |
| `failed` | генерация упала; причина — в `generationError` (строка на русском), `document` остался плейсхолдером |

`generationError` присутствует всегда, при `pending`/`ready` равен `null`.

Идентификатор фоновой задачи генерации **совпадает с `id` приложения**, поэтому статус можно опрашивать и через `GET /api/tasks/{id}`, ничего дополнительно не сохраняя.

## Статус фоновой задачи — `GET /api/tasks/[id]`

Генерический эндпоинт поверх статуса джобы в Arq/Redis, не привязан к приложениям (тем же способом будет опрашиваться будущий zip-экспорт). Отвечает всегда 200, в том числе для неизвестного `id`:

```json
{ "id": "8c90a14f-…", "status": "complete", "result": null, "error": null }
```

| Поле | Значения |
|---|---|
| `status` | `deferred` / `queued` / `in_progress` / `complete` / `not_found` — как их отдаёт `arq.jobs.Job.status()` |
| `result` | результат задачи, если она завершилась успешно; у генерации результата нет — `null` |
| `error` | текст исключения, если задача завершилась с ошибкой, иначе `null` |

`not_found` возвращается и для несуществующей задачи, и для завершённой, у которой в Redis уже истёк срок хранения результата, — различить их нельзя. Для приложений источник правды о результате — `generationStatus` в `GET /api/apps/[id]`, а `/api/tasks/[id]` нужен, чтобы видеть, взята задача в работу или ещё стоит в очереди.

Сама генерация на бэкенде — MVP-заглушка: выбор одного из пяти шаблонов (`habits` / `social` / `shop` / `forms` / `blank`) по ключевым словам в промпте, без LLM. См. открытый вопрос ниже.

Модель `AppDocument` (и всё, что вокруг неё — `AppNode`, `AppThemeTokens`, дерево, нормализация) типизирована и валидируется zod-схемами в `frontend/packages/api/src/apps/model.ts` — это перенесённые из рабочего прототипа реальные поля (`colorBg`, `colorPrimary`, `navigation.roots` и т.д.), не придуманные заново. При изменении формы документа на бэке правь оба места синхронно: этот файл и `model.ts`.

В прототипе `PUT` валидировался бэком минимально (`Array.isArray(document.screens) && document.theme`) и никакой авторизации не было (заголовок `x-user-id`, по умолчанию `'anonymous'`) — это не образец для копирования, а фиксация того, что было. В FastAPI-версии обе вещи стоит сделать по-настоящему (Pydantic-модели на входе, реальная авторизация), не повторяя прототип буквально.

## Не специфицировано ни в ТЗ, ни в прототипе

- Канал чата с ассистентом (отправка сообщения, стриминг ответа, карточки предложений/коммитов) — в прототипе AI-чат в редакторе вообще не ходит ни в какую LLM, только локальный regex-парсер команд поверх стора. Нет ни эндпоинта, ни протокола, который стоило бы копировать. Пока фронт эту часть не реализует по-настоящему — `frontend/packages/api` не содержит `chat`-модуля, только `apps`.
- Эндпоинт/механизм загрузки файлов и изображений (вложения в промпт и в чат, «Мои файлы» в редакторе) — в прототипе это тоже только метаданные без реальной загрузки.
- Генерация `AppDocument` из промпта — на бэкенде реализован template-подход (пять шаблонов, выбор по ключевым словам, дефолт `blank`), это осознанная MVP-заглушка в `backend/src/generation/`. Настоящая LLM-генерация JSON документа — отдельная задача; контракт от неё не изменится, меняется только начинка `generate_document`.
- Авторизация — см. предупреждение выше.
