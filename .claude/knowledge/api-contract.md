# API-контракт фронт↔бек

Источник: раздел 5 ТЗ плюс сверка с рабочим прототипом (Next.js-версия продукта, которую делал предыдущий разработчик — там эти эндпоинты реально реализованы и работают на Drizzle/SQLite). Это отправная точка для FastAPI-реализации Егора, не финальная спецификация — он может её скорректировать, тогда правь и этот файл синхронно с `frontend/packages/api/src/apps/queries.ts`.

## Эндпоинты — формы запроса/ответа проверены по рабочему коду

| Метод | Путь | Тело запроса | Тело ответа |
|---|---|---|---|
| GET | `/api/apps` | — | `{ apps: AppSummary[] }` — `AppSummary = { id, name, slug?, updatedAt }`, сортировка по `updatedAt desc` |
| POST | `/api/apps` | `{ prompt: string, name?: string }`, `prompt.length >= 3` | `{ id: string }`, статус 201 |
| GET | `/api/apps/[id]` | — | `{ id, name, slug?, document: AppDocument, generationStatus, generationError? }` |
| PUT | `/api/apps/[id]` | `AppDocument` целиком | `{ ok: true, document: AppDocument }`; 409, пока `generationStatus === "pending"` |
| DELETE | `/api/apps/[id]` | — | `{ ok: true }` или 404 |
| GET | `/api/apps/[id]/export` | — | `application/zip` прямо в ответе, не JSON; заголовок `Content-Disposition: attachment; filename="<slug>.zip"` |
| GET | `/api/tasks/[id]` | — | `{ id, status, result?, error? }` — статус фоновой задачи |

Все ответы об ошибках — JSON с полем `error`, человекочитаемый текст на русском.

## Асинхронная генерация приложения

`POST /api/apps` **форму ответа не меняет** — по-прежнему `{ id }` и 201. Но приложение создаётся сразу, с пустым плейсхолдер-документом (валидная тема, `screens: []`) и полем `generationStatus: "pending"`, а сама генерация уходит в очередь Arq. Клиент получает `id` немедленно и открывает редактор, не дожидаясь генерации.

`generationStatus` в ответе `GET /api/apps/[id]` — одно из трёх значений:

| Значение | Что означает |
|---|---|
| `pending` | документ ещё генерируется, в `document` лежит плейсхолдер без экранов |
| `ready` | генерация закончилась, в `document` готовое приложение |
| `failed` | генерация упала; причина — в `generationError` (строка на русском), `document` остался плейсхолдером |

`generationError` присутствует всегда, при `pending`/`ready` равен `null`.

Идентификатор фоновой задачи генерации **совпадает с `id` приложения**, поэтому статус можно опрашивать и через `GET /api/tasks/{id}`, ничего дополнительно не сохраняя.

**Пока `generationStatus === "pending"`, документом владеет воркер, а не клиент.** Плейсхолдер — не документ пользователя, а заглушка, которую генератор заменит целиком, поэтому:

- `PUT /api/apps/[id]` в этом состоянии отвечает **409** «Приложение ещё генерируется, сохранение недоступно» и документ не трогает. Иначе клиент, открывший редактор до конца генерации, сохранял бы обратно плейсхолдер поверх сгенерированного приложения (реально случившийся баг: автосохранение фронта затирало результат воркера через 1200 мс после открытия редактора).
- Фронт не показывает редактор и не заводит автосохранение, пока статус `pending`: `useApp` опрашивает `GET /api/apps/[id]` раз в 800 мс и отдаёт документ в стор только при `ready` (при `failed` показывается `generationError`).

Защита односторонняя: она закрывает окно генерации, но **не** решает общий случай потерянного обновления (два клиента, устаревший документ у вкладки, висевшей в фоне). Для этого нужна оптимистичная блокировка — версия документа в `PUT` и 409 при расхождении; пока не сделана, зафиксировать решение здесь, когда дойдут руки.

## Статус фоновой задачи — `GET /api/tasks/[id]`

Генерический эндпоинт поверх статуса джобы в Arq/Redis, не привязан к приложениям (zip-экспорт через него не опрашивается — см. ниже, он синхронный). Отвечает всегда 200, в том числе для неизвестного `id`:

```json
{ "id": "8c90a14f-…", "status": "complete", "result": null, "error": null }
```

| Поле | Значения |
|---|---|
| `status` | `deferred` / `queued` / `in_progress` / `complete` / `not_found` — как их отдаёт `arq.jobs.Job.status()` |
| `result` | результат задачи, если она завершилась успешно; у генерации результата нет — `null` |
| `error` | текст исключения, если задача завершилась с ошибкой, иначе `null` |

`not_found` возвращается и для несуществующей задачи, и для завершённой, у которой в Redis уже истёк срок хранения результата, — различить их нельзя. Для приложений источник правды о результате — `generationStatus` в `GET /api/apps/[id]`, а `/api/tasks/[id]` нужен, чтобы видеть, взята задача в работу или ещё стоит в очереди.

Сама генерация на бэкенде (BIL-15) — LLM-запрос в RouterAI, OpenAI-совместимый шлюз. Шаблоны, которые стояли здесь раньше, из прода убраны и живут только в тестовых фикстурах. Для контракта важно вот что:

- **Фоллбэка на шаблоны нет.** Не задан ключ RouterAI, упала сеть, шлюз отклонил запрос, модель за все попытки не вернула валидный `AppDocument` — приложение уходит в `generationStatus: "failed"`, а причина в `generationError` (по-русски). Клиент никогда не получает «что-нибудь похожее вместо ничего», поэтому обработка `failed` на фронте обязательна, а не декоративна.
- **Повторы прячутся внутри задачи.** Невалидный ответ модели скармливается ей же обратно вместе с текстом ошибки валидации — до `ROUTERAI_MAX_RETRIES` попыток (по умолчанию 3, это общее число попыток). Наружу это не видно: статус так и остаётся `pending`, пока попытки идут, поэтому генерация может занимать заметно дольше одного запроса к модели, и поллинг `GET /api/apps/[id]` раз в 800 мс на это рассчитан.
- Ключ, база и модель настраиваются переменными окружения `ROUTERAI_API_KEY` / `ROUTERAI_BASE_URL` / `ROUTERAI_MODEL` (шаблон — `backend/.env.example`). Модель по умолчанию — `deepseek/deepseek-v4-flash`, **вживую не проверена**: ключа на момент задачи не было. Подробности и что перепроверить с ключом — в [`backend/architecture.md`](backend/architecture.md#91-генерация-документа-routerai).

Модель `AppDocument` (и всё, что вокруг неё — `AppNode`, `AppThemeTokens`, дерево, нормализация) типизирована и валидируется zod-схемами в `frontend/packages/api/src/apps/model.ts` — это перенесённые из рабочего прототипа реальные поля (`colorBg`, `colorPrimary`, `navigation.roots` и т.д.), не придуманные заново. При изменении формы документа на бэке правь оба места синхронно: этот файл и `model.ts`.

Незаданные опциональные поля документа (`style.padding`, `props.text`, `layout.zIndex`, `screen.icon`, `slug`, `prompt`, …) и `slug` в `AppSummary` бэк **не сериализует вовсе** — ключа в JSON просто нет, `null` вместо него не приходит. Это не косметика: в `model.ts` все такие поля объявлены `.optional()` и ни одно не `.nullable()`, поэтому `null` роняет `parse` на реальных документах. Исключение — `generationError` в `GET /api/apps/[id]`: он присутствует всегда и при `pending`/`ready` равен `null` (см. выше). На бэке за это отвечает базовая модель `OmitNoneModel` в `backend/src/apps/schemas.py` — новые модели дерева документа наследуй от неё, а не от `CamelModel`.

В прототипе `PUT` валидировался бэком минимально (`Array.isArray(document.screens) && document.theme`) и никакой авторизации не было (заголовок `x-user-id`, по умолчанию `'anonymous'`) — это не образец для копирования, а фиксация того, что было. В FastAPI-версии обе вещи стоит сделать по-настоящему (Pydantic-модели на входе, реальная авторизация), не повторяя прототип буквально.

## Экспорт Expo-проекта — `GET /api/apps/[id]/export`

Для клиента эндпоинт **синхронный**: в ответе сразу тело архива (`application/zip`), фронт просто открывает ссылку (`getExportUrl` + `window.location.href`), никакого поллинга и никакого `taskId`. Ошибки — как везде, JSON с полем `error`: 404 «Приложение не найдено», 504 если сборка не уложилась в таймаут (30 с).

Асинхронность спрятана внутри: обработчик ставит задачу сборки в очередь Arq и ждёт её результат, а не собирает zip сам — CPU-работа идёт в процессе воркера и не занимает event loop API. Идентификатор задачи здесь — свежий `uuid4()` (у одного приложения может быть много независимых экспортов), поэтому опрашивать его через `/api/tasks/{id}` бессмысленно, клиент его и не видит.

Содержимое архива строит **порт TS-генератора на Python** (`backend/src/codegen/service.py` ← `frontend/apps/web/src/entities/app-document/lib/codegen.ts`): те же файлы, те же пути, то же содержимое — `package.json`, `app.json`, `tsconfig.json`, `babel.config.js`, `.gitignore`, `theme.ts`, `app/state.tsx`, `app/_layout.tsx`, `app/<route>.tsx` на каждый экран (`index` → `app/index.tsx`), `README.md`. Совпадение с панелью кода в редакторе держится тестом на равенство вывода обоих генераторов (Node нужен только этому тесту в CI, в прод-рантайм бэкенда он не попадает). **Меняешь один генератор — меняй второй в том же PR.**

## Чат ассистента (BIL-36, BIL-37)

Хранение истории сообщений домена `chat`, чтение, решение по предложению («предложение» → «коммит» из `product.md`, раздел 3.3) — BIL-36. Сам разговор с LLM (отправка сообщения пользователем и генерация ответа ассистента с опциональной правкой документа) — BIL-37. **Это и есть финальное решение по «протоколу чата», который до BIL-37 был открытым вопросом:** никакого SSE и WebSocket — та же схема «поставили задачу, отдали `taskId`, клиент поллит `/api/tasks/{id}`», что уже работает у генерации приложения. Стриминга ответа по токенам нет и не планируется в этом срезе: ответ ассистента появляется в истории целиком, когда задача завершилась.

| Метод | Путь | Тело запроса | Тело ответа |
|---|---|---|---|
| GET | `/api/apps/{app_id}/chat/messages` | — | `{ messages: ChatMessage[] }`, хронологический порядок; 404, если приложения нет |
| POST | `/api/apps/{app_id}/chat/messages` | `{ content: string }` — обрезается по краям, после обрезки длина от 3 до 4000 символов | `{ taskId: string }`, статус **202**; 404, если приложения нет; 409, пока `generationStatus === "pending"`; 422 при невалидном теле |
| POST | `/api/apps/{app_id}/chat/messages/{message_id}/decision` | `{ accepted: boolean }` | `{ ok: true, message: ChatMessage }`; 404 «Сообщение не найдено», 409, если сообщение — не предложение ассистента (`role !== "assistant"` или нет `proposedDocument`) |

`ChatMessage`:

```
{
  id: string
  role: "user" | "assistant"
  content: string
  proposedDocument: AppDocument | null
  accepted: boolean | null
  createdAt: string
}
```

`proposedDocument` и `accepted` ведут себя как `generationError` у `AppDetailResponse`, а не как опциональные поля внутри `AppDocument`: ключ в JSON присутствует всегда, `null` — это «предложения нет» / «решение ещё не принято», а не отсутствующее значение. Так фронт различает состояния без обращения к `role`. Это осознанное решение по аналогии с уже принятым для `generationError` — не путать с конвенцией `.optional()`/не-`.nullable()` полей самого `AppDocument`.

### Ход диалога — `POST /api/apps/{app_id}/chat/messages`

Статус ответа — **202, а не 201**: это не создание финального ресурса, а принятая в обработку задача. Сообщение пользователя записывается в историю синхронно, ответ ассистента появится в ней позже.

`content` перед проверкой длины обрезается по краям (`strip`), и в историю попадает уже обрезанным: сообщение из одних пробелов — это 422, а не валидная реплика. Верхняя граница 4000 символов стоит там же и по той же причине, по которой есть нижняя: реплика целиком уходит в промпт модели.

Что происходит по шагам:

1. Приложение проверяется на `generationStatus`. Пока он `pending` — **409** «Приложение ещё генерируется, сохранение недоступно» (тот же гейт и тот же текст, что у `PUT /api/apps/[id]`): обсуждать документ, которого ещё нет, нечего.
2. Сообщение пользователя сразу пишется в историю **и транзакция коммитится** — сразу после ответа `GET .../chat/messages` уже показывает его с `proposedDocument: null`. Коммит именно здесь, до постановки задачи: воркер — отдельный процесс и может взять джобу раньше, чем запись видна в БД (подробности и размен — в [`backend/architecture.md`](backend/architecture.md#коммит-до-постановки-задачи)).
3. В очередь Arq ставится задача `chat_turn` — ей передаются `app_id` и `message_id` только что записанной реплики. Остальной контекст она собирает сама, но собирает его **на момент этой реплики**, а не на момент своего запуска (зачем — см. ниже). **`job_id` — свежий `uuid4()`, а не `id` приложения** (в отличие от генерации, где они намеренно совпадают): у одного приложения ходов диалога сколько угодно, и они независимы. Именно этот `uuid4()` возвращается как `taskId`.
4. Клиент поллит `GET /api/tasks/{taskId}` — эндпоинт генерический, никакого отдельного чат-специфичного статуса не заводили.

**Как читать статус задачи.** `status` идёт от `arq.jobs.Job.status()` и становится `complete`, когда задача *завершилась*, — успешно или нет. Признак провала — непустой `error`, а не отдельный статус:

| Что видит клиент | Что произошло |
|---|---|
| `status: "queued"` / `"in_progress"` | ответ ещё генерируется |
| `status: "complete"`, `error: null` | ответ готов — перечитать `GET .../chat/messages` |
| `status: "complete"`, `error: "…"` | ход провалился, текст причины в `error` |
| `status: "not_found"` | задачи нет либо результат уже вытек из Redis (различить нельзя) |

**При провале сообщение ассистента просто не создаётся** — в истории остаётся только реплика пользователя. Никакого аналога `generationStatus: "failed"` на уровне `ChatMessage` нет и заводить его не стали: у приложения статус генерации нужен, потому что документ-плейсхолдер существует и его надо как-то пометить, а здесь помечать нечего — сообщения ассистента просто нет. Единственный источник правды о провале хода — `error` в `/api/tasks/{taskId}`, поэтому фронт обязан его читать, а не только ждать `complete`.

**Что модель возвращает внутри задачи** — `ChatTurnResponse`, наружу по HTTP эта форма не выходит (клиент видит результат уже как `ChatMessage`):

```
{
  reply: string
  document: AppDocument | null
}
```

`reply` обрезается по краям и обязан быть непустым: пустая или пробельная реплика не проходит валидацию `ChatTurnResponse` и уходит модели на повтор наравне с любым другим невалидным ответом (см. ниже) — сообщение ассистента с пустым текстом в историю попасть не может.

`document` заполняется, **только когда ассистент реально предлагает правку**; на вопрос или обычную реплику приходит один `reply`, и сообщение ассистента ложится в историю с `proposedDocument: null`. Когда `document` есть, он попадает в `proposedDocument` — дальше обычный путь BIL-36: пользователь принимает или отклоняет через `POST .../decision`. **Документ приходит целиком, не патчем и не диффом.**

**Контекст, который уходит в модель:** системный промпт (роль ассистента + JSON Schema `ChatTurnResponse`, внутри которой лежит и схема `AppDocument` — отдельно она не сериализуется, чтобы не дублировать её в промпте), текущий документ приложения и история переписки — **последние 20 сообщений, существовавших на момент отправки этой реплики**, только `role` и `content`. Всё, что легло в историю позже, в контекст этого хода не попадает. Это видно клиенту: если отправить второе сообщение, не дождавшись ответа на первое, ассистент ответит на каждое по отдельности, а не сольёт их в один ответ. Вложенные `proposedDocument` прошлых сообщений в контекст не идут: каждый из них — целый документ, и пары таких сообщений хватило бы, чтобы разорвать окно модели. Актуальное состояние приложения ассистент видит из текущего документа, а не из истории предложений.

**Повторный запуск хода дублей не создаёт.** Если Arq перезапустит задачу, ответ на эту реплику всё равно окажется в истории ровно один: у ответа ассистента хранится ссылка на реплику, которой он отвечает, и на неё стоит уникальный констрейнт в БД. Наружу это поле не выходит — в `ChatMessage` его нет, форма ответа не меняется. Для клиента это значит только одно: повторное `complete` по тому же `taskId` не требует никакой дедупликации на его стороне.

Невалидный ответ модели скармливается ей обратно вместе с текстом ошибки валидации — тот же retry-цикл и тот же лимит `ROUTERAI_MAX_RETRIES`, что у генерации приложения (общий код — `backend/src/generation/structured_output.py`, параметризован целевой Pydantic-моделью). Наружу повторы не видны: задача остаётся в работе, пока попытки идут.
