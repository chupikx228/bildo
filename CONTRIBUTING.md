# Как работать с репозиторием

Ветки, коммиты и пул-реквесты. Правила общие для фронтенда и бэкенда.

## Ветки

`main` — всегда рабочая: в неё не пушим напрямую, только через пул-реквест. Всё остальное — короткоживущие ветки от `main`.

```
<тип>/BIL-<номер>/<краткое-описание-через-дефисы>
```

Тип — тот же, что у коммита (см. ниже). Ключ задачи — заглавными, ровно как в Jira. Описание на латинице, в нижнем регистре, 2–5 слов по сути задачи.

```
feat/BIL-42/inspector-set-var
fix/BIL-118/logo-jump-on-apps-page
refactor/BIL-203/canvas-drag-handlers
docs/BIL-77/api-contract-chat-protocol
```

Ключ обязателен: по нему Jira сама привязывает ветку, коммиты и пул-реквест к задаче и двигает её статус. Ветка без ключа в задаче не появится — связывать руками потом никто не будет.

Без задачи в Jira ветку заводим только на мелочь, которую не заводят в трекер (`chore/bump-react-19-2`, `ci/fix-pnpm-cache-path`). Всё, что видит пользователь, задачу имеет.

Ветка живёт до мержа и удаляется сразу после. Долгоживущих веток вроде `develop` у нас нет: команда маленькая, ветвление плоское.

## Коммиты — Conventional Commits

```
<тип>(<область>): <описание>

[тело — зачем, если неочевидно]

[футер — breaking changes, ссылки]
```

Заголовок: до ~72 символов, **на английском**, в повелительном наклонении, без точки в конце. Тип и область тоже английские — они часть спецификации, и по ним строится история.

**Язык.** Весь текст коммита — заголовок и тело — на английском. То же для имён веток и заголовков PR. На русском в репозитории остаётся только документация: `.claude/knowledge/`, этот файл, README, тексты ошибок в коде.

```
feat(inspector): add "set variable" action on press

BIL-42
```

Ключ задачи — отдельной строкой в футере, через пустую строку после заголовка или тела. В заголовок его не тащим: заголовок читают люди, футер читает Jira.

```
feat(inspector): add "set variable" action on press
fix(canvas): don't move the node on a single click
refactor(assistant): move the collapsed rail into the widget
docs(api-contract): document the assistant chat protocol
chore(deps): bump vite to 8.2
ci: run backend architecture contracts on PRs
```

### Типы

| Тип | Когда |
|---|---|
| `feat` | новая функциональность для пользователя |
| `fix` | исправление бага |
| `refactor` | правка кода без изменения поведения |
| `perf` | оптимизация |
| `style` | форматирование, не влияющее на смысл |
| `docs` | документация, включая `.claude/knowledge/` |
| `test` | тесты |
| `build` | сборка, зависимости |
| `ci` | пайплайны |
| `chore` | всё остальное, что не попадает в историю изменений продукта |
| `revert` | откат коммита |

### Области

Фронтенд: `web`, `api` (это `packages/api`), `editor`, `canvas`, `inspector`, `assistant`, `files`, `code-panel`, `landing`.
Бэкенд: `backend`, `apps`, `generation`, `codegen`, `chat`, `files`.
Общее: `deps`, `ci`, `docs`.

Область необязательна, если правка не привязана к одному месту.

### Ломающие изменения

Восклицательный знак после области и футер:

```
feat(api)!: rename colorPrimary to colorAccent

BREAKING CHANGE: frontend and backend must update together;
old documents are normalized on read.
```

## Задачи в Jira

Ключ задачи — `BIL-<номер>`, всегда заглавными: `BIL-42`, не `bil-42` и не `Bil42`. В нижнем регистре Jira его не распознаёт, и связка с задачей молча не сработает.

Где ключ обязан быть — три места, каждое даёт свою связь:

| Где | Зачем |
|---|---|
| Имя ветки | Jira показывает ветку в задаче и предлагает создать PR |
| Футер коммита | коммиты видны в панели разработки задачи |
| Заголовок PR — в конце, в скобках | пул-реквест привязывается к задаче и двигает её статус |

```
feat(inspector): add "set variable" action on press (BIL-42)
```

Статус двигает тот, кто делает задачу, — не ждём, что это сделает кто-то другой на стендапе:

| Когда | Статус |
|---|---|
| Взял в работу, завёл ветку | **In Progress** |
| Открыл пул-реквест | **In Review** |
| PR смержен в `main` | **Done** |
| Ждём ответа заказчика, чужого PR, доступа | **Blocked**, и в комментарии — чего именно ждём |

Одна задача — одна ветка — один PR. Если задача разрослась, дробим её в Jira на подзадачи, а не тащим три несвязанные правки в одну ветку.

Если PR закрывает несколько задач, ключи перечисляются в футере коммита по строке на каждый, а в заголовке PR — через запятую: `(BIL-42, BIL-43)`.

> Названия статусов взяты стандартные. Если на доске колонки называются иначе — поправьте таблицу под реальный воркфлоу, ключ `BIL-` от этого не меняется.

## Что обязано ехать в одном коммите

Есть пары файлов, которые расходятся молча — и это ловится не тестами, а только на проде. Их правим вместе:

- **Форма `AppDocument`** → `frontend/packages/api/src/apps/model.ts` + Pydantic-схемы бэкенда + [`.claude/knowledge/api-contract.md`](.claude/knowledge/api-contract.md).
- **Любой эндпоинт** (путь, тело запроса, тело ответа) → код + `api-contract.md`.
- **Новый домен на бэкенде** → код + контракты `[tool.importlinter]` в `backend/pyproject.toml`. Не впишешь — домен просто не проверяется, и это тихая дыра, а не ошибка сборки.
- **Решение по открытому вопросу** (авторизация, протокол чата, загрузка файлов) → фиксируется в `.claude/knowledge/`, а не только в переписке.

## Пул-реквесты

Перед пушем прогони проверки локально — CI гоняет ровно их, и упасть в пайплайне за то, что ловится за 10 секунд на машине, обидно:

```bash
cd frontend && pnpm check
cd backend && make check
```

`pnpm fix` и `make fix` чинят всё автоисправимое.

Заголовок PR — как заголовок коммита плюс ключ задачи в конце: `feat(inspector): add "set variable" action on press (BIL-42)`. В описании: что меняется и зачем; если правился интерфейс — скриншот до/после.

Один PR — одна задача. Рефакторинг соседнего кода «заодно» выносится в отдельный PR: смешанный диф невозможно ревьюить.

## Что проверяет CI

Пайплайны фильтруются по путям: правишь только фронт — бэковый не запускается.

- **frontend** — Prettier, ESLint (включая границы слоёв FSD), `tsc`, прод-сборка.
- **backend** — ruff format, ruff lint, mypy strict и архитектурные контракты: слои `router → service → repository`, инверсия зависимостей, границы доменов.

Красный CI не мержим.
